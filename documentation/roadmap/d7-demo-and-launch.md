**Status:** planned; the last milestone of v1.0. Starts after D6 is tagged. **Depends on:**
- D5: the server; `CHECKPOINT` arrives here;

- M8: the engine report and the workload rules;

**Goal.** Make the whole claim visible in five minutes:

## 1. The application: "Shelf", a small library-lending app

### 1.1 Schema (created at first start; every query below is in D3's `demo_queries.slt`)

```sql
CREATE TABLE members (id BIGINT PRIMARY KEY, name TEXT NOT NULL, email TEXT NOT NULL);
CREATE UNIQUE INDEX members_by_email ON members (email);
CREATE TABLE books (id BIGINT PRIMARY KEY, title TEXT NOT NULL, author TEXT NOT NULL,
                    isbn TEXT NOT NULL, copies BIGINT NOT NULL, available BIGINT NOT NULL);
CREATE INDEX books_by_author ON books (author);
CREATE INDEX books_by_title ON books (title);
CREATE UNIQUE INDEX books_by_isbn ON books (isbn);
CREATE TABLE loans (id BIGINT PRIMARY KEY, book_id BIGINT NOT NULL, member_id BIGINT NOT NULL,
                    loaned_at BIGINT NOT NULL, due_at BIGINT NOT NULL, returned_at BIGINT);
CREATE INDEX loans_by_due ON loans (due_at);
CREATE INDEX loans_by_member ON loans (member_id);
```

- **Ids** are random positive 63-bit values generated by the app, so there are no sequences to
  contend on. A collision → `23505` → the app retries with a new id.
- **Times** are epoch milliseconds (there is no timestamp type).

### 1.2 Features, and the SQL behind each

| Feature | SQL | What it demonstrates |
|---|---|---|
| Browse books, 20 per page | `SELECT … FROM books ORDER BY title LIMIT 20 OFFSET $1` | order from `books_by_title`, no sort |
| Search by author / title prefix | `WHERE author = $1` / `WHERE title LIKE $1` (`'dune%'`) | index scan; the `LIKE` prefix range |
| Add, edit, delete a book or member | `INSERT` / `UPDATE … WHERE id = $1` / `DELETE … WHERE id = $1` | point access; index maintenance (visible in the cost line) |
| Check out a book | `BEGIN; SELECT available … WHERE id = $1; UPDATE books SET available = available - 1 WHERE id = $1; INSERT INTO loans …; COMMIT` | serializable OCC; retry on `40001` |
| Return a book | `BEGIN; UPDATE loans SET returned_at = $2 WHERE id = $1; UPDATE books SET available = available + 1 WHERE id = $3; COMMIT` | a multi-statement transaction |
| Overdue loans | `SELECT … FROM loans WHERE due_at < $1 AND returned_at IS NULL` | index range scan plus residual filter |
| A member's loans, with titles | `SELECT … FROM loans l JOIN books b ON l.book_id = b.id WHERE l.member_id = $1` | index nested-loop join |
| Stats | `SELECT author, COUNT(*) FROM books GROUP BY author ORDER BY 2 DESC LIMIT 5`; loans per member | hash aggregate, top-N |

- **The checkout conflict, made visible.** Two browser tabs check out the last copy together. Both
  read `available = 1`; one commits. The other's `COMMIT` fails with `40001`. The app retries once
  with a fresh read, sees `available = 0`, and shows "already taken".
- **Retry policy:** at most 3 attempts on `40001`, each with a fresh transaction.

### 1.3 How it is built

- **Backend:** `dev.shale.demo`, on the JDK's `com.sun.net.httpserver`.
  - **Checkstyle:** the JDK-ban `IllegalImport` module gets `id="bannedJdkApis"`, and a
    `SuppressionSingleFilter` suppresses it for `shale-demo/…/DemoHttpServer.java` only
    (ADR-0013).
  - **Endpoints:** `GET` pages; `POST` with form-encoded bodies; responses in JSON from a 60-line
    hand-written writer (the demo only ever writes JSON, never parses it).
  - **Data access:** pgjdbc, and parameterised SQL only.
  - **Connections:** a fixed pool of 4, a `BlockingQueue` of `Connection`s. There is no pool
    library.
  - **Cost notices:** every pooled connection runs `SET shale.cost_notices = on` once.
- **Frontend:** static HTML, CSS and plain JavaScript served from resources. No framework and no
  build step.
- **"What did that cost?"** Every API response carries the cost notice lines of the statements it
  ran (read from `Statement.getWarnings()`). The UI shows them in a collapsible drawer under each
  action. Nothing is ever executed twice.
- **Engine panel:** every second, `GET /api/engine` runs `SELECT * FROM shale_levels` and `SELECT
  * FROM shale_metrics`. The page draws:
  - files and bytes per level;
  - compaction debt;
  - write amplification;
  - flush, compaction and stall counts;
  - group-commit size;
  - commits and aborts.

  A "generate load" button starts a server-side loop of random checkouts and returns for 30
  seconds, so the panel visibly moves.

### 1.4 Scripts

- **`scripts/demo.sh`:** build, start `bin/shaledb` on a temp directory, start the demo on port
  8080, seed 2,000 books and 200 members (fixed seed), print the URL.
- **`scripts/crash-demo.sh`,** running `CrashDemo.main` in `shale-demo`:
  1. start the server as a child process;
  2. run checkouts with `synchronous_commit = on`, appending each **acknowledged** loan id to a
     list;
  3. SIGKILL the server (`ProcessHandle.destroyForcibly()`) after a seeded number of
     acknowledgements;
  4. restart it;
  5. assert every acknowledged loan exists, `SELECT * FROM shale_verify` returns no rows, and every
     book's `available` equals `copies` minus its open loans;
  6. print `PASS`, or the missing ids.
- **`docker-compose.yml`:** the server and the demo, for machines with only Docker.

### 1.5 `CHECKPOINT`

The D2 grammar gains `CHECKPOINT`, PostgreSQL's own command. ShaleDB defines it as
`engine.flush()` then `engine.compactRange(null, null)` (M6 §2.7). It returns tag `CHECKPOINT`.
The findings use it to reach a known compacted shape.

### 1.6 `BACKUP TO` — an online backup through SQL

`BACKUP TO 'name'` calls `engine.checkpoint(<backup-dir>/name)` (M8 §2.6) and returns tag `BACKUP`.
The copy is consistent, taken while the server keeps serving, and is itself a data directory:
restoring is `bin/shaledb --dir <backup-dir>/name`.

**It is a ShaleDB extension.** PostgreSQL's online backup is `pg_basebackup`, a client of the
replication protocol, which is out of scope. The guides say so.

**Safety.** The server has no authentication, so a client must not choose where the server writes.
- The server writes backups only inside `--backup-dir`. Without that flag, `BACKUP` is `0A000`.
- `name` must match `[a-z0-9_-]{1,63}`, so it cannot contain a path. Anything else is `22023`.
- An existing name is `42710`.

**Transactions:** inside a transaction block, it is `25001`, as `VACUUM` is in PostgreSQL. A
checkpoint is not transactional.

## 2. The findings (the SQL-level measurements)

- **Harness:** in `shale-bench`, a `SqlStore` interface with two embedded implementations:
  - `ShaleDbSqlStore`: `Session`, in-process;
  - `SqliteSqlStore`: the `sqlite-jdbc` driver, WAL mode, `synchronous=FULL`.

  Both run the Shelf schema and the same statements.
- **Rules:** M8's — seeded, 3 runs per point, the environment recorded, charts as Mermaid
  `xychart-beta`.
- **The report:** `documentation/benchmarks/sql.md`, one section per finding: the question, the
  method, the chart, and the answer in one sentence.

| # | Question | Method |
|---|---|---|
| F1 | What does an `INSERT` really cost as indexes are added? | 100,000 inserts into `books` with 0, 1, 2, 3 secondary indexes. Per insert: keys written, WAL bytes, p50/p99 latency (from cost notices and timers). After `CHECKPOINT`: write amplification |
| F2 | Are deletes free? | Delete 50% of `loans`; full-scan latency and `tombstones_skipped` before and after `CHECKPOINT` |
| F3 | Leveled or tiered for this application? | 10 minutes of the Shelf mix (70% browse and search, 20% checkouts, 10% returns) under each style: p50/p99 per statement type; write and space amplification |
| F4 | What do bloom filters buy a SQL workload? | F1's inserts (uniqueness checks) and point lookups, at `bloomBitsPerKey` 0 vs 10 |
| F5 | Where does ShaleDB stand? | The F3 mix on SQLite: throughput and p99, reported as context, not competition |

## 3. The launch

### 3.1 The README (rewritten last, from what exists)

1. The pitch, in one line.
2. A 60-second GIF: `psql` → `EXPLAIN ANALYZE` of an `INSERT` → the app with its cost drawer →
   `crash-demo.sh` printing `PASS`.
3. "Run it in 60 seconds": `scripts/demo.sh`, or `docker compose up`.
4. The architecture diagram.
5. Two headline charts: one from M8, one from F1–F5.
6. The verification story: crash tests at every byte and file operation, the model tests, the
   SQL logic and differential tests, the serializability checker, the real `kill -9`.
7. **"Use it": three doors**, each one command and one link:
   - **try the demo:** `scripts/demo.sh`;
   - **use the database** from any PostgreSQL client: `guides/shaledb-quickstart.md`;
   - **embed the engine** in a JVM application: `guides/embedding-shale.md`.
8. The status, and the docs map (with the FAQ).
9. **A build note:** how the project was built, including the AI assistance. The project's claim
   is understanding, so saying how it was built strengthens it.

### 3.2 Write-ups (`documentation/writeups/`, each ≤ 1,500 words, with diagrams)

- "What an INSERT costs on an LSM, measured" (F1, F4, the cost notices).
- "Testing crash consistency at every byte and every file operation" (M1, M5, D5).
- "SQL on a key-value engine: encoding, planning, and serializable OCC" (D1–D4).
- **The retrospective** (`documentation/retrospective.md`), written last and honestly:
  - what was hardest, and why;
  - which estimates were wrong, from the completion plan's actual-vs-estimate column;
  - the bugs that mattered, from the bug log;

  with evidence rather than improvisation. The FAQ's last answer links to it.

## 4. Steps

### Step 1 — `CHECKPOINT` and `BACKUP TO` (`d07/checkpoint`), ~2 days
1. `feat(sql)`: grammar and execution of both; `Database.checkpoint(Path)`; the server's
   `--backup-dir`.
2. **Tests:**
   - `checkpoint.slt`: after `CHECKPOINT`, `shale_levels` shows one populated level and zero debt.
   - `BackupTest`, through pgjdbc against an in-process server:
     - a backup taken while another connection inserts opens as a consistent database, and
       `verify()` is clean;
     - no `--backup-dir` → `0A000`;
     - `'../x'` → `22023`;
     - an existing name → `42710`;
     - inside `BEGIN` → `25001`.
3. `docs(guides)`: backup and restore in `shaledb-quickstart.md`; `BACKUP TO` in `shaledb-sql.md`.

**Done when:** green.

### Step 2 — the module and the backend (`d07/backend`), ~4 days
1. `build(demo)`: the module (pgjdbc runtime; the `bannedJdkApis` suppression; the
   `verifyModuleGraph` rule that `shale-demo` has no project dependencies).
2. `feat(demo)`: schema bootstrap, the seed generator, the pool, the JSON writer, every §1.2
   endpoint, retry on `40001`, cost-notice collection.
3. **Tests** (against an in-process `ShaleDbServer`):
   - `ShelfApiTest`: every endpoint;
   - `CheckoutConflictTest`: two concurrent checkouts of the last copy → exactly one loan, the
     other told "already taken";
   - every response carries its cost lines.

**Done when:** green.

### Step 3 — the frontend and the engine panel (`d07/frontend`), ~4 days
`feat(demo)`: pages, the cost drawer, the engine panel, the load button. Checked by hand, with a
short checklist in the commit body; a Playwright script is not worth its weight here.
**Done when:** the checklist passes in Chromium and Firefox.

### Step 4 — the scripts (`d07/scripts`), ~2 days
`build(demo)`: `demo.sh`, `CrashDemo` + `crash-demo.sh`, `docker-compose.yml`. `build(ci)`: a CI
job runs `crash-demo.sh` with a fixed seed. **Done when:** `crash-demo.sh` prints `PASS` 20 of 20
seeds locally, and in CI.

### Step 5 — the findings (`d07/findings`), ~5 days
1. `feat(bench)`: `SqlStore`, `ShaleDbSqlStore`, `SqliteSqlStore` (sqlite-jdbc pinned,
   `shale-bench` only), and the Shelf workload mix.
2. Run F1–F5; write `documentation/benchmarks/sql.md`.

**Done when:** each finding has a chart, its environment, its reproduction command and a
one-sentence answer.

### Step 6 — the README, write-ups, tour and retrospective (`d07/launch-docs`), ~5 days
§3.1–§3.3, and a final pass over the FAQ and every guide, so that no answer still says "planned"
for something that shipped. **Done when:** every README claim links to its evidence — a test, a
chart or an ADR — and every link resolves.

### Step 7 — the fresh-clone check (`d07/fresh-clone`), ~1 day
On a clean Linux machine and a clean macOS machine (or container):
- `git clone`, then `scripts/demo.sh`, reaching a working app in under five minutes with only JDK
  25 installed;
- then `docker compose up`, with only Docker installed;
- then each guide followed literally, as a new user would:
  - `embedding-shale.md` §2–§4;
  - `shaledb-quickstart.md`: `psql`, JDBC and Python.

  Every command must work as written; any that does not is fixed in the guide or the code.

Record both in the release notes. **Done when:** both pass.

### Step 8 — the release (`d07/release`), ~1 day
`build(ci)`: tag triggers. A final changelog entry; the completion plan's status table all ✅;
tag `v1.0`; a GitHub release. **Done when:** CI is green on the tag.

## 5. Milestone acceptance gates

- A fresh clone reaches a working demo in under five minutes (with JDK 25 only, or with Docker
  only).

- F1–F5 each have a chart and a one-sentence answer.
- Every claim in the README links to its evidence.
