# M5.5 — Concurrent write path: implementation plan

**Status:** proposed implementation plan, 2026-09-10; no implementation or accepted ADR.
**Depends on:** completed M5 and a measured synchronous baseline. Grounded in `9cfa7d6`,
ADR-0008, Durability, WalWriter and the current Shale write/read paths. Reconcile this plan
with M5's actual interfaces before coding; no speculative public API or format is prescribed.

**Goal:** concurrent durable requests share force operations, flush runs in the background,
and bounded admission prevents memory growth without weakening write guarantees.

## Entry gate and M5 contracts

M5 must provide durable file-set installation, explicit WAL replay ownership, safe read-view
pinning, obsolete-file reclamation, a failed/closed state and deterministic file fault injection.
Require `build crashTest` green and exercise these contracts before adding threads:

- Installing a flush retires precisely its source memtable/WAL ownership, while concurrent
  active writes and newer read views remain intact.
- A WAL cannot close/delete while append, force, recovery or an uninstalled memtable owns it.
- Manifest installation is serialized independently of long table writes; a caller can prepare
  an edit outside a short state lock, persist it, then publish against current state safely.
- Both point reads and cursors acquire a view safely; resource lifetime is separate from
  snapshot semantics, which still arrive at M7.
- Failed force/install retains recoverable inputs, rejects subsequent writes and wakes waiters.

If M5 lacks one of these, add a focused prerequisite fix rather than duplicating its machinery.

## Proposed ADR-0013 decisions

Use the next available ADR number if 0013 has been taken. Acceptance follows review of M5.

1. **Preserve ordering.** ADR-0008 requires WAL append → force for SYNC/GROUP → memtable
   insertion → acknowledgement. The older assessment's append+insert under lock followed by
   force violates this contract. Recommend queued requests and an ordered publication stage.
   NONE requires append before insertion but may wait behind earlier durable requests to keep
   publication simple. Earlier visibility is an alternative requiring explicit contract changes,
   not an incidental optimization. Reads gain no snapshot guarantee in this milestone.
2. **Writer leadership.** Recommend one queued-request leader owning append/framing and force
   at a time. Producers enqueue under a short state lock; the leader detaches a bounded cohort,
   assigns sequences in queue order, appends outside that lock, forces if needed, then publishes
   successful requests in sequence order and completes them. No proactive sleep to grow batches.
   Pending callers retain/copy input according to a documented ownership contract until return.
3. **Alternatives.** Compare that design with appending concurrent followers during force using
   per-segment offsets and force generations. The latter can overlap more work but needs proof
   that a force covers each acknowledged record. Do not claim early followers are covered merely
   because they completed append before force returned. Prefer the single owner initially;
   benchmark before adopting more overlap.
4. **Mode semantics.** Recommend both SYNC and GROUP may share a force, retaining their same
   durable-before-return guarantee. NONE-only cohorts do not force; mixed cohorts may make NONE
   durable incidentally. Document ordering-induced delay and partial-cohort failure semantics.
   One force over a cohort is not atomic WriteBatch support; that remains M7.
5. **Locks and I/O.** Publish an ownership/lock table. No state lock spans append, force, table
   write, rename, manifest I/O, executor submission, future completion or condition waiting.
   The older phrase “WAL append under a short lock” still places file I/O under that lock.
   Logical leader ownership may span I/O; waiting producers must release the state lock.
6. **Bounds.** Bound cohort bytes/count, pending request bytes/count and immutable bytes/count,
   including an in-progress flush. Decide defaults from baseline workloads. Define an oversized
   request policy consistent with existing accepted input sizes; do not add a silent size limit.
   Charge the request before retaining an internal copy. Admission waits without reserving a
   sequence or holding the state lock; failure/close wakes every waiter.
7. **Rotation.** Recommend cohorts stay within one WAL ownership epoch; an oversized first
   request may cross the memtable target under a documented one-request overshoot policy.
   Freeze only after assigned records are published. Force users finish before segment close.
   The frozen memtable retains its WAL until M5 installs its output durably.
8. **Flush.** One injected, named worker processes immutable memtables FIFO initially, preserving
   the current source-age assumptions. Release queue accounting only after installation. Build
   the new view from current state under serialization, never from a stale pre-I/O copy.
   A stalled writer cannot prevent the flush worker from making the progress that releases it.
9. **Failure/interrupt.** Preserve the first storage failure, reject new writes and finish/wake
   pending requests consistently. An append/force error may leave surviving unacknowledged data;
   do not retry blindly. Specify cancellation before enqueue versus interruption after ownership
   transfer: an interrupted wait must not imply that a logged write was rolled back.
10. **Close.** Specify OPEN → CLOSING → CLOSED, with FAILED behavior orthogonal or explicitly
    enumerated. Stop admission, resolve queued/in-flight writes, drain background work, then
    release files. Decide final active flush versus WAL-only close in the ADR and reconcile the
    existing shutdown convention. Do not close a channel to make a stuck force appear complete.
    If shutdown has a timeout, report incomplete cleanup honestly; deterministic tests use an
    injected deadline and ordering gates, not wall-clock latency assertions.

## Work packages and exit tests

| Order | Deliverable | Required evidence |
|---|---|---|
| 0 | Baseline harness, before mechanism changes | Durable write and read-during-flush results with commit/JDK/hardware/configuration |
| 1 | ADR, state/ownership diagram, lock table | Resolve D3 ordering, mode semantics, queue bounds, interruption and shutdown |
| 2 | Serialized WAL append separated from force internally | Existing WAL bytes/golden unchanged; partial append/force failure covered |
| 3 | Bounded writer queue and single cohort leader | Controlled cohort shares force; no durable completion or visibility before force |
| 4 | Memtable rotation and per-segment ownership | Delayed force cannot race WAL close; sequence order survives rotation |
| 5 | Injected FIFO flush worker and admission stalls | Writes progress while capacity exists; full capacity blocks without deadlock |
| 6 | Integrate failure and close lifecycle | Every waiter terminates under failure/close; no leaked handles/tasks |
| 7 | Model, crash matrix and measurement | Acknowledged durability preserved; before/after results; build/crash gates green |
| 8 | As-built docs and release note | Remove reserved GROUP wording only after batching works; update conventions/status |

Each work package should produce reviewable, green commits. Internal test seams must not
require widening StorageBackend. If a public configuration API is needed, settle it in the ADR.
No WAL/SSTable format change is intended; any actual byte change invokes the format rules.

## Deterministic scenarios

- Hold leadership until N durable requests are queued, release one bounded cohort, assert one
  force and N successes after publication. Separately verify solitary SYNC and GROUP progress.
- Pause force: concurrent readers cannot observe that cohort's SYNC/GROUP versions. After
  success, put/delete acknowledgements imply visibility unless a later write superseded them.
- Append a NONE-only cohort without force, then mix modes; validate required acknowledgements
  and restart results against the correct process-crash and modeled power-loss guarantees.
- Hold flush at table write and at manifest installation. Writers progress with remaining
  capacity, then stall exactly at the configured bound. Release flush and prove wakeup.
- Rotate across several cohorts while a cursor pins an old view. Verify ordered reads,
  correct final overwrites/tombstones and WAL/table retention through durable installation.
- Fail append, force, task submission, table write or manifest install; no waiter hangs and no
  failed durable request reports success. Reopen includes all acknowledged durable writes.
- Race close with admission, force, flush and pinned readers. Check chosen completion/error
  semantics, idempotent close and zero outstanding owned resources after pins are released.
- Exercise oversized requests, queue accounting and interrupted callers; no dropped request,
  reused sequence, counter underflow or unbounded internal accumulation.

Keep real-thread stress coverage, including overwrites and deletes, alongside controlled tests.
Seeds reproduce operation choices; schedule traces/gates reproduce interleavings. Do not call
ordinary seeded thread stress deterministic simulation, or require every production run to batch.

## Measurement and finish

JMH declares forks/warmup/measurement and consumes results. Use shared engine state for
concurrent writers, isolated directories per trial, controlled dataset growth and identical
settings across revisions. Report NONE/SYNC/GROUP separately at 1/2/4/8 writers, force count
per write, throughput and suitable latency distributions. Include reads during forced flush.
Exclude setup/teardown and record buffer sizes, storage device and durability mode.

Metrics: cohort count/size, force count/duration, pending/immutable bytes, stall count/duration,
flush backlog/duration and failures. Use injected Clock for durations; no new runtime logging
or metrics dependency. Tests assert event ordering/counters, not benchmark speed thresholds.

Exit: `./gradlew build crashTest`; complete controlled scenarios; no unbounded queue; preserved
format fixtures; recorded before/after measurements with limitations. M6 begins only after
this gate. The next planning task is M6 file selection, tombstone retention and point-read
correctness, grounded in M5/M5.5's final Version and scheduling interfaces.
